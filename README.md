# ربات نمایندگان پنل 🤖

ربات تلگرامی که به پنل **PasarGuard API v5** وصل می‌شود و **پنل نمایندگی** می‌فروشد:
هر خریدار یک حساب اپراتور روی پنل می‌گیرد، می‌تواند چند پنل داشته باشد، آن‌ها را
شارژ کند، برای مشتریانش **کانفیگ تست رایگان** بگیرد و پنل موجودش را هم به ربات
وصل کند.

**همهٔ خریدها به‌صورت خودکار روی پنل اعمال می‌شوند** — بدون نیاز به دخالت سوپرادمین.

> ⚠️ **برای فروش پنل نمایندگی، `panel.owner_username` و `panel.owner_password` را در
> `config.php` تنظیم کنید.** بدون آن، فروشگاه پنل نمایندگی با پیام
> «موقتاً در دسترس نیست» بسته می‌ماند (شارژ پنل همچنان کار می‌کند).
> گزارش `php tools/healthcheck.php` این مورد را به‌صورت **خطا** گزارش می‌کند.

## چه کاری انجام می‌دهد؟

| **چند پنل برای هر نماینده** | هر کاربر می‌تواند چند پنل داشته باشد؛ هر پنل یک ردیف مستقل در جدول `panels` |

### دو نوع بسته

**۱) بستهٔ پنل نمایندگی (`agency`)**
با پرداخت، یک حساب اپراتور تازه روی پنل ساخته و اطلاعات کاملش به خریدار
نمایش داده می‌شود:
```
سفارش → پرداخت → POST /api/admin  →  حساب rep{orderId}  →  ذخیره در panels
```
نام کاربری **قطعی** است (`rep{orderId}`)، پس اگر ساخت روی پنل موفق شود ولی ذخیرهٔ
محلی شکست بخورد، تلاش مجدد همان حساب را پیدا می‌کند و حساب دوم نمی‌سازد.

> **نقش اپراتور خودکار پیدا می‌شود.** طبق اسپک PasarGuard، فیلد `role_id` در
> `POST /api/admin` **اجباری** است و بدون آن ۴۲۲ می‌گیرید. اگر
> `panel.rep_role_id` را تنظیم نکرده باشید، ربات از `GET /api/admin-roles` یک نقش
> **غیرمالک** (ترجیحاً اپراتور) پیدا می‌کند. نقش مالک (`is_owner`) **هرگز**
> خودکار داده نمی‌شود. اگر پنل فقط نقش مالک داشته باشد، خرید **fail-fast** متوقف
> می‌شود (بدون تلاش مجدد بیهوده) و به شما می‌گوید یک نقش اپراتور بسازید.

**۲) بستهٔ شارژ پنل (`topup`)**
حجم و زمان به‌صورت **مطلق** به یکی از پنل‌های کاربر اضافه می‌شود (نه نسبی، تا
شارژ دوباره حجم را دوبار نشمارد). اگر کاربر چند پنل داشته باشد، اول پنل هدف را
انتخاب می‌کند.

> **چرا زمان در دیتابیس ربات است؟** در API پنل، حساب ادمین فیلد `expire` ندارد و فقط
> `data_limit` دارد. بنابراین مدت اعتبار در دیتابیس ربات مدیریت و نمایش داده می‌شود.

> **ساخت کاربر از داخل ربات حذف شد.** بستهٔ قدیمی `user_credit` در مایگریشن ۰۰۵
> غیرفعال شده و ابزار «ساخت/تمدید کاربر» دیگر وجود ندارد؛ نماینده فقط کاربران
> مشتریانش را **مستقیماً روی پنل خودش** مدیریت می‌کند.

## سقف کاربران هر بسته 🎯

جدا از حجم (گیگابایت) و مدت (روز)، هر بسته می‌تواند یک **سقف تعداد یوزر** بفروشد:
«با این بستهٔ ۱۰۰ گیگی، حداکثر ۵۰ یوزر می‌توانی روی پنل بسازی.»

| ستون | معنی |
|---|---|
| `packages.max_users` | سقفی که بسته می‌فروشد — `0` یعنی نامحدود ♾️ |
| `orders.max_users` | اسنپ‌شات همان سقف در لحظهٔ خرید (بعداً تغییر بسته روی سفارش اثر ندارد) |
| `panels.user_limit` | سقف خریداری‌شدهٔ هر پنل |

قواعد:

- خرید `agency` ⇒ سقف روی پنل تازه **ست** می‌شود.
- خرید `topup` ⇒ سقف با بستهٔ جدید **جمع** می‌شود، ولی **نامحدود غالب است**:
  بستهٔ نامحدود پنل محدود را نامحدود می‌کند و پنل نامحدود را بستهٔ محدود
  محدود نمی‌کند.
- جمع‌زدن سقف **idempotent** است (`markPanelApplied`) — تلاش مجدد بعد از موفقیت
  ناقص، سقف را دو بار بالا نمی‌برد.
- معیار «پر شدن»، تعداد **کاربران ساخته‌شده** (`users_total`) است نه فعال‌ها،
  چون لیمیت روی «ساخت» اعمال می‌شود.
- کرون هم به خریدار و هم به مدیر هشدار می‌دهد (کلید ضدتکرار شامل خودِ سقف است تا
  با هر شارژ، هشدار تازه برود).

هنگام ساخت/ویرایش بسته از داخل ربات، بخش ششم اختیاری است:

```
عنوان | نوع | حجم_گیگ | مدت_روز | قیمت_تومان | سقف_کاربران
```

```
پنل ۱۰۰ گیگ ۳۰ روزه | agency | 100 | 30 | 500000 | 50
```

نبودن بخش ششم یعنی نامحدود ♾️.

## کلیدهای فعال/غیرفعال (سوییچ‌ها)

همهٔ این موارد از **پنل مدیریت** (⚙️ تنظیمات) یا خط فرمان قابل تغییرند و نیازی به
دست‌زدن به کد یا دیتابیس نیست.

| سوییچ | کلید در `settings` | مسیر در ربات |
|---|---|---|
| **کل ربات** | `bot_enabled` | ⚙️ تنظیمات → فعال/غیرفعال کردن ربات |
| **متن غیرفعالی** | `bot_disabled_notice` | ⚙️ تنظیمات → ✏️ متن غیرفعالی |
| **کارت‌به‌کارت** | `gateway_card2card` | 💳 مدیریت درگاه‌های پرداخت |
| **کارت خودکار** | `gateway_autocard` | 💳 مدیریت درگاه‌های پرداخت |
| **ارز دیجیتال** | `gateway_nowpayments` | 💳 مدیریت درگاه‌های پرداخت |
| **تمدید** | `renewal_enabled` | ⚙️ تنظیمات |
| **همگام‌سازی پنل** | `panel_sync_cron` | ⚙️ تنظیمات → 🔄 همگام‌سازی |
| **تست کانفیگ** | `test_config_enabled` | ⚙️ تنظیمات → 🧪 تست کانفیگ |
| **قطع پس از انقضا** | `cutoff_on_expire` | ⚙️ تنظیمات → ✂️ قطع پس از انقضا |
| **عضویت اجباری کانال** | `channel_enforced` | ⚙️ تنظیمات → 📡 عضویت اجباری |
| **کد تخفیف** | `coupons_enabled` | ⚙️ تنظیمات → 🎟️ کد تخفیف |
| **معرفی** | `referral_enabled` | ⚙️ تنظیمات → 🎁 معرفی |
| **تیکت پشتیبانی** | `tickets_enabled` | ⚙️ تنظیمات → 🎫 تیکت |
| **فروشگاه** | `shop_opened` | ⚙️ تنظیمات |
| **اجرای خودکار** | `auto_apply` | ⚙️ تنظیمات |

مقادیر عددی این قابلیت‌ها از **🚀 رشد و نگهداشت** در پنل مدیریت تنظیم می‌شوند:
مهلت ارفاقی انقضا، درصد و مبلغ پاداش معرفی، و عمر حافظهٔ آمار کاربران پنل.

### نکات مهم

> **سوپرادمین‌ها همیشه دسترسی دارند.** حتی وقتی کل ربات خاموش است، سوپرادمین‌ها
> می‌توانند وارد پنل مدیریت شوند و ربات را دوباره روشن کنند — وگرنه ربات برای همیشه
> خاموش می‌ماند.

> **درگاه «پیکربندی‌نشده» کار نمی‌کند.** اگر در `config.php` شماره کارت یا کلید
> NOWPayments یا آدرس سرویس استعلام کارت خودکار را وارد نکرده باشید، روشن کردن
> سوییچ آن بی‌فایده است. پنل این وضعیت را با عبارت «پیکربندی نشده» نشان می‌دهد.

> **خاموش کردن آخرین درگاه** هشدار می‌دهد، چون در آن حالت کاربران نمی‌توانند
> پرداخت کنند.

### از خط فرمان

```bash
php tools/switches.php list                      # نمایش وضعیت همه
php tools/switches.php bot off                   # خاموش کردن کل ربات
php tools/switches.php bot on                    # روشن کردن
php tools/switches.php gateway card2card off     # کارت‌به‌کارت
php tools/switches.php gateway autocard off      # کارت خودکار
php tools/switches.php gateway nowpayments on    # ارز دیجیتال
php tools/switches.php renewal off               # تمدید
php tools/switches.php sync off                  # همگام‌سازی خودکار پنل‌ها
php tools/switches.php testconfig off            # تست کانفیگ
php tools/switches.php cutoff off                # قطع پس از انقضا
php tools/switches.php channel on                # عضویت اجباری کانال
php tools/switches.php channel-name "@MyChannel" # تنظیم کانال
php tools/switches.php coupons off               # کدهای تخفیف
php tools/switches.php referral off              # سیستم معرفی
php tools/switches.php tickets on                # تیکت پشتیبانی
php tools/switches.php grace-days 5              # مهلت ارفاقی انقضا
php tools/switches.php warn-days 7               # چند روز قبل از انقضا هشدار
php tools/switches.php referral-percent 15       # تخفیف معرفی
php tools/switches.php referral-bonus 80000      # پاداش معرف (تومان)
php tools/switches.php low-volume 10             # آستانهٔ حجم کم (درصد)
php tools/switches.php test-volume 2             # حجم هر کانفیگ تست (گیگ)
php tools/switches.php notice "در حال تعمیرات"  # تغییر متن غیرفعالی
php tools/switches.php notice --reset            # بازگردانی متن پیش‌فرض
```

وضعیت فعلی در گزارش سلامت هم دیده می‌شود:

```bash
php tools/healthcheck.php
```

## جریان خرید

### الف) خرید «پنل نمایندگی» (ساخت حساب تازه)

```
نمایندهٔ تازه            ربات                     پنل PasarGuard          سوپرادمین
  │                       │                            │                     │
  ├─ /start ─────────────>│                            │                     │
  │<─ منوی اصلی ──────────┤                            │                     │
  ├─ 🛒 خرید پنل ────────>│                            │                     │
  │<─ فهرست بسته‌ها ──────┤                            │                     │
  ├─ 🛒 خرید این بسته ──>│                            │                     │
  │<─ انتخاب درگاه ───────┤                            │                     │
  │  (کارت / کارت خودکار  │                            │                     │
  │   / ارز دیجیتال)       │                            │                     │
  │  ── یا ارسال رسید ───>│─────────────────────────────>│──── رسید جدید ─────>│
  │                       │                            │<─ تأیید رسید ───────┤
  │                       │─── POST /api/admin ───────>│                     │
  │<─ ✅ حساب rep{id} ─────┤<── حساب + رمز جدید ───────│                     │
  │<─ آدرس/نام/رمز پنل ──┤                            │                     │
```

پس از ساخت، نماینده **اطلاعات کامل پنل** (آدرس ورود، نام کاربری، رمز، حجم،
سقف کاربران، زمان) را در بخش «🖥️ پنل‌های من» می‌بیند.

### ب) ثبت پنل از قبل موجود

```
ادمین (نماینده نیست)      ربات                     پنل PasarGuard
  │                       │                            │
  ├─ 🔗 من پنل دارم ─────>│                            │
  │<─ نام کاربری؟ ────────┤                            │
  ├─ نام کاربری ─────────>│                            │
  │<─ رمز عبور؟ ──────────┤                            │
  ├─ رمز عبور ───────────>│─── GET /api/admin/token ─>│
  │                       │<── access_token ───────────│
  │<─ ✅ پنل متصل شد ──────┤<── مشخصات پنل ───────────│
```

اگر آن پنل قبلاً به حساب دیگری در ربات وصل شده باشد، ربات آن را رد می‌کند و
کاربر به پشتیبانی ارجاع می‌شود.

### پ) شارژ پنل موجود

```
  ├─ ⚡️ شارژ پنل ────────>│  (اگر چند پنل داشته باشد، اول انتخاب پنل)
  ├─ 🛒 خرید این بسته ──>│─── GET /api/admin ───────>│
  │                       │─── PUT /api/admin ───────>│  (سقف/زمان مطلق)
  │<─ ✅ بسته اجرا شد ────│                            │
```

برای پرداخت ارز دیجیتال، تأیید مستقیم از طریق **IPN** انجام می‌شود و نیازی به
دکمهٔ تأیید سوپرادمین نیست.

### ت) کارت‌به‌کارت خودکار (مبلغ یکتا) ⚡️💳

```
  ├─ ⚡️ کارت خودکار ─────>│  مبلغ یکتا = قیمت + چند رقم آخر رندوم
  │                       │  مثلاً ۵۰۰٬۰۰۰ → ۵۰۰٬۳۴۷ تومان
  ├─ واریز همان مبلغ ────>│
  │                       │  کرون / دکمهٔ «🔄 بررسی وضعیت»
  │                       │─── استعلام سرویس کارت ───>│
  │<─ ✅ تأیید و اجرا ────│<── تراکنش با همان مبلغ ───│
```

مبلغ یکتا باعث می‌شود هر واریز دقیقاً به **همان یک** سفارش نسبت داده شود؛ کاربر
رسید نمی‌فرستد و نیازی به تأیید دستی نیست. اگر پنل کارت (یا سرویس استعلام)
پیکربندی نشده باشد، این درگاه اصلاً در فهرست پرداخت به کاربر نشان داده نمی‌شود.

### ث) چرخهٔ عمر پنل نمایندگی (با مهلت ارفاقی)

```
خرید ──> فعال ──> هشدار حجم کم ──> هشدار انقضای نزدیک (خریدار + مدیر)
  │           │              │
  │           │              └──> انقضا ──> 🚨 هشدار «مهلت ارفاقی»
  │           │                              │
  │           │              (۳ روز فرصت تمدید)│
  │           │                              ↓
  │           │                    پایان مهلت ──> درخواست قطع دسترسی به مدیر
  │           │                                       ↓ تأیید مدیر
  │           │                          غیرفعال شدن همهٔ کاربران آن پنل
  │           ↓
  └──> 🎫 تست کانفیگ رایگان   👥 آمار کاربران پنل   🎯 سقف کاربران پر شد
      🧾 فاکتور خرید          💰 کیف پول و تاریخچه پرداخت‌ها
```

> **چرا مهلت ارفاقی؟** انقضا یعنی «قرارداد تمام شد» ولی نه لزوماً «همین الان
> باید سرویس مردم را قطع کرد». اگر تاریخ اشتباه محاسبه شده باشد یا نماینده
> چند ساعت بعد از انقضا شارژ کند، قطع فوری یعنی قطع خدمت مردم و شکایت.
> مقدار پیش‌فرض **۳ روز** است؛ با `expire_grace_days = 0` به رفتار قبلی برمی‌گردد.
>
> **هشدار مهم:** غیرفعال کردن کاربران روی پنل **قابل بازگشت نیست** — نه با
> دکمهٔ «بازگشت» و نه با شارژ دوباره. مهلت ارفاقی را قبل از اولین انقضای جدی
> تنظیم کنید.

## تخفیف، معرفی، کیف پول و فاکتور

### کد تخفیف 🎟️

از پنل مدیریت: **🎟️ کد تخفیف** → ➕ کد تخفیف جدید. فرمت ورودی:

```
کد | نوع | مقدار | حداکثر_استفاده | سقف_تخفیف | توضیح
```

| نمونه | معنی |
|---|---|
| `SUMMER \| percent \| 20 \| 100 \| 200000` | ۲۰٪ تخفیف، حداکثر ۱۰۰ نفر، حداکثر ۲۰۰ هزار تومان |
| `OFF500 \| fixed \| 50000 \| 0 \| 0` | ۵۰ هزار تومان تخفیف نقدی، نامحدود |

کاربر از دکمهٔ «🎟️ کد تخفیف» کد را وارد می‌کند و روی **خرید بعدی** اعمال
می‌شود (حتی اگر فردا بخرد — کد روی رکورد کاربر ذخیره می‌شود، نه در نشست).

- مصرف کد **اتمیک** است: دو خرید همزمان نمی‌توانند سقف را دور بزنند.
- `per_user_limit` (پیش‌فرض ۱) جلوی استفادهٔ مکرر یک کاربر را می‌گیرد.
- تخفیف هرگز از کل مبلغ بیشتر نمی‌شود و **حداقل مبلغ خرید بعد از تخفیف**
  بررسی می‌شود، پس بستهٔ رایگان ساخته نمی‌شود.
- اگر کد بین ثبت و پرداخت باطل شود، قیمت اصلی محاسبه می‌شود و خرید قفل
  نمی‌شود.

### معرفی دوستان 🎁

هر کاربر کد قطعی `R{id}` دارد و لینک دعوتش:

```
https://t.me/<YourBot>?start=R123
```

- دوستِ معرفی‌شده در **اولین** خریدش `referral_discount_percent` تخفیف می‌گیرد.
- معرف به ازای هر خرید **پرداخت‌شدهٔ** معرفی‌شده `referral_bonus_toman` به کیف
  پیف پولش اضافه می‌شود (کرون، نه لحظهٔ ثبت سفارش — وگرنه پاداش بی‌پرداخت
  هم داده می‌شد).
- یک کاربر تازه فقط یک معرف دارد و خودمعرفی رد می‌شود.
- اگر کاربر کد تخفیف فعال داشته باشد، **کد تخفیف برنده است** و تخفیف‌ها روی
  هم جمع نمی‌شوند.

### کیف پول 💰👛

هر کاربر یک کیف پول تومانی دارد که از دو راه پر می‌شود:

- **پاداش معرفی** — خودکار توسط کرون، فقط برای خرید پرداخت‌شده.
- **شارژ/کسر دستی** — فقط سوپرادمین، از «👥 کاربران ← کاربر ← 💰👛 شارژ/کسر کیف پول».

منوی «💰👛 کیف پول» موجودی و ۱۰ تراکنش آخر را نشان می‌دهد و هر تراکنش با
برچسب دلیلش (`manual` / `referral`) ثبت می‌شود. موجودی هرگز منفی نمی‌شود؛
کسر بیش از موجودی فقط تا صفر انجام می‌شود.

> کیف پول در حال حاضر فقط **اعتبار** است و در فاکتور خرید مصرف نمی‌شود؛
> پرداخت با کیف پول هنوز فعال نیست (نوع تراکنش `wallet_pay` در کد رزرو شده ولی
> هیچ مسیری آن را صدا نمی‌زند).

### فاکتور 🧾

در صفحهٔ هر سفارش پرداخت‌شده دکمهٔ «🧾 فاکتور خرید» هست. لینک فاکتور به
`invoice.php?t=<token>` می‌رود و یک صفحهٔ HTML چاپ‌پذیر است (دکمهٔ
«چاپ / ذخیره PDF»). فونت **وزیرمتن** داخل پروژه (`assets/fonts`) میزبانی
می‌شود تا فاکتور آفلاین هم درست چاپ شود.

> دسترسی با **توکن ۱۲۸ بیتی** محافظت می‌شود، نه شمارهٔ سفارش — چون لینک بین
> نماینده و مشتری او دست‌به‌دست می‌شود. توکن قابل حدس نیست.

## تیکت پشتیبانی 🎫

کاربر از منوی اصلی: **🎫 پشتیبانی** → انتخاب موضوع (پرداخت / پنل / حساب /
تست کانفیگ / پیشنهاد / سایر) → نوشتن متن.

- مدیر همان لحظه اعلان می‌گیرد (با دکمهٔ «باز کردن تیکت»).
- پاسخ مدیر **هم داخل تیکت** و **هم به‌صورت پیام برای کاربر** فرستاده می‌شود —
  وگرنه کاربر فکر می‌کند جواب نداده‌اید.
- کاربر می‌تواند زیر پاسخ مدیر بنویسد یا تیکت را ببندد.
- تیکت بسته با یک پاسخ جدید دوباره باز می‌شود.

پنل مدیریت: **🎫 پشتیبانی** در صفحهٔ اصلی، و تعداد تیکت‌های باز همان‌جا نمایش
داده می‌شود.

## ربات مدیریتی جدا (اختیاری) 🤖

اگر یک ربات دوم بسازید، سوپرادمین‌ها می‌توانند از آن استفاده کنند و
ترافیکشان از صف کاربران جدا بماند:

```bash
# در config.php:
'admin_bot_token'      => 'توکن ربات دوم',
'admin_webhook_secret' => 'یک رشتهٔ تصادفی متفاوت از webhook_secret',

php tools/cli.php set-webhook-admin
```

| مزیت | توضیح |
|---|---|
| جداسازی ترافیک | کوئری‌های سنگین پنل مدیریت، صف کاربران را شلوغ نمی‌کنند |
| امنیت بیشتر | می‌توانید ربات دوم را در گروه محدود کنید یا آیدی مدیران را روی آن قفل کنید |
| بازیابی | اگر ربات اصلی خراب شود، مدیریت از راه ربات دوم ممکن است |

دروازه‌های `admin.php`:
1. ربات دوم پیکربندی نشده ⇒ `503`
2. توکن امنیتی غلط ⇒ `403`
3. فرستنده سوپرادمین نیست ⇒ **بی‌صدا نادیده گرفته می‌شود** (تا ربات دوم
   اسپم‌بان نشود)

اگر پیکربندی نکنید، `admin.php` فقط `503` می‌دهد و هیچ اتفاقی نمی‌افتد.

## بکاپ قبل از تغییر پرریسک 💾

**قبل از هر مایگریشن جدید یا تغییر ساختاری، یک بکاپ بگیرید:**

```bash
php tools/cli.php backup            # بکاپ فوری
php tools/cli.php backup --keep=30  # سقف نگهداری ۳۰ نسخه
php tools/cli.php backup --prune    # فقط پاک‌سازی نسخه‌های قدیمی
```

بکاپ‌ها در `data/backups/bot-backup-<تاریخ>.sqlite` ساخته می‌شوند و
`tools/install.sh` هم **قبل از مایگریشن** به‌صورت خودکار یکی می‌سازد.

سقف نگهداری پیش‌فرض ۱۴ نسخه است و از پنل مدیریت (💾 بکاپ) یا خط فرمان قابل
تغییر است. پشتیبانی خودکار روزانه با کرون (`backup_schedule` = `off`/`daily`/`twice`)
فایل را برای سوپرادمین‌ها هم ارسال می‌کند.

> ⚠️ بکاپ شامل **رمز پنل‌های رمزنگاری‌شده** است. آن را جایی نگه ندارید که لو برود —
> با لو رفتن، رمز همهٔ پنل‌های نمایندگان قابل رمزگشایی است.

## نصب سریع

### پیش‌نیازها
- PHP **8.1+** با افزونه‌های `pdo_sqlite`، `curl`، `json`، `mbstring`، `openssl`
- دامنه با HTTPS (تلگرام وبهوک را روی HTTP قبول نمی‌کند)
- دسترسی SSH برای کرون (اختیاری ولی برای اطمینان توصیه می‌شود)

### نصب با اسکریپت (توصیه‌شده)

```bash
bash tools/install.sh
```

اسکریپت **فقط سه سؤال** می‌پرسد و بقیه را خودکار انجام می‌دهد:

| # | سؤال | چه می‌نویسد |
|---|---|---|
| ۱ | توکن ربات از `@BotFather` | `bot_token` |
| ۲ | آیدی عددی تلگرامی شما | `super_admins` |
| ۳ | آدرس وب سایت (بدون اسلش انتهایی) | `base_url` |

بقیهٔ کارها بدون پرسش انجام می‌شود:

- ساخت `config.php` از قالب (اگر نبود)
- تولید `crypto_key`، `webhook_secret` و `admin_webhook_secret` — فقط وقتی
  هنوز مقدار نمونه داشته باشند؛ **هرگز** کلیدی که قبلاً تنظیم شده عوض نمی‌شود
- بکاپ دیتابیسِ موجود، سپس مایگریشن و ساخت بسته‌های پیش‌فرض
- تأیید توکن با `getMe` و نوشتن خودکار `bot_username`
- ثبت وبهوک اصلی (و وبهوک مدیریتی اگر `admin_bot_token` تنظیم شده باشد)
- اجرای `tools/healthcheck.php` و گزارش پایانی

اعتبارسنجی ورودی هم داخل اسکریپت هست؛ مثلاً توکن بدون `:` یا آدرس بدون
`https://` پذیرفته نمی‌شود و دوباره پرسیده می‌شود.

بدون تعامل (مناسب CI یا نصب مجدد):

```bash
BOT_TOKEN=123456789:AAH... ADMIN_ID=123456789 BASE_URL=https://bot.example.com \
  bash tools/install.sh
```

> ⚠️ اگر ثبت وبهوک شکست بخورد (مثلاً سرور به `api.telegram.org` دسترسی
> نداشته باشد) اسکریپت با **کد خروج ۱** تمام می‌شود و پیام «نصب انجام شد ولی
> وبهوک ثبت نشد» چاپ می‌کند — هرگز پیام موفقیت چاپ نمی‌کند مگر اینکه واقعاً
> موفق شده باشد. بعد از رفع مشکل:

```bash
php tools/cli.php set-webhook     # کد خروج ۱ یعنی ناموفق
php tools/cli.php get-me          # ۰=توکن درست، ۱=نامعتبر، ۲=بدون شبکه
```

> ℹ️ اگر سرور Bot API خودتان را راه انداخته‌اید، `telegram_api_base` را در
> `config.php` روی پایهٔ آن بگذارید (مثل `http://localhost:8081` یا
> `http://localhost:8081/bot` — هر دو قبول است، «/bot» خودکار اضافه می‌شود).
> خالی یعنی `api.telegram.org`.

### نصب دستی

#### گام ۱ — کپی و پیکربندی

```bash
git clone <repo-url>
cd "Pasargad Representatives' Bot Telegram"
cp config.example.php config.php
```

سپس `config.php` را ویرایش کنید:

```php
'bot_token'      => 'توکن از @BotFather',
'super_admins'   => [123456789],           // آیدی عددی شما
'base_url'       => 'https://bot.example.com',
'webhook_secret' => 'یک-رشته-تصادفی-طولانی',
'crypto_key'     => 'یک-رشته-تصادفی-دیگر-حداقل-۳۲-کاراکتر',
'bot_username'   => 'MyBot',
```

> ⚠️ **`webhook_secret` اجباری است.** اگر خالی بماند یا همان مقدار نمونهٔ
> `CHANGE-THIS-RANDOM-SECRET` باقی بماند، `bot.php` **همهٔ درخواست‌ها را با
> ۴۰۳ رد می‌کند** و ربات اصلاً کار نمی‌کند. این عمدی است: بدون این توکن، هر
> کسی می‌توانست یک update جعلی بفرستد، خود را سوپرادمین جا بزند و بسته بسازد
> یا سفارش تأیید کند.
>
> برای ساخت مقدار مناسب:
>
> ```bash
> php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
> ```

برای تولید `crypto_key` هم دقیقاً همین دستور را اجرا کنید — کلید رمزنگاری
رمزهای پنل کاربران است و باید حداقل ۳۲ کاراکتر باشد.

#### گام ۲ — نصب دیتابیس و بسته‌های پیش‌فرض

```bash
php tools/cli.php migrate
php tools/seed.php
```

#### گام ۳ — تست اتصال پنل

```bash
php tools/cli.php health
php tools/healthcheck.php
```

`healthcheck.php` بخش‌های تنظیمات، دیتابیس، پنل، پرداخت، سوییچ‌ها، وبهوک،
بکاپ، کرون و فروشگاه را بررسی می‌کند و با کد خروج غیرصفر تمام می‌شود اگر
خطایی باشد (مناسب برای مانیتورینگ).

#### گام ۴ — تنظیم وبهوک

```bash
php tools/cli.php set-webhook
```

بررسی وضعیت:
```bash
php tools/cli.php webhook-info
```

#### گام ۵ — کرون (مهم)

```cron
*/5 * * * * php /path/to/cron/worker.php
```

#### گام ۶ — تست

```bash
php tools/run_tests.php
```

| `bot_username` | نام کاربری ربات بدون `@` (برای لینک بازگشت درگاه) |

| `super_admins` | آیدی عددی سوپرادمین‌های ربات |
| `admin_bot_token` | توکن ربات مدیریتی دوم (اختیاری؛ خالی ⇒ `admin.php` غیرفعال) |

### ساخت بسته از داخل ربات

در پنل مدیریت روی «➕ بستهٔ جدید» بزنید و این فرمت را بفرستید:

```
عنوان | نوع | حجم_گیگ | مدت_روز | قیمت_تومان | سقف_کاربران
```

مثال:
```
پنل نمایندگی ۵۰ گیگ ۳۰ روزه | agency | 50 | 30 | 500000 | 50
```

- نوع‌ها: `agency` (پنل نمایندگی — حساب تازه می‌سازد) یا `topup` (شارژ پنل موجود).
  نام‌های فارسی («پنل نمایندگی»، «شارژ») هم پذیرفته می‌شوند.
- بخش ششم (**سقف کاربران**) اختیاری است؛ نبودش یعنی نامحدود ♾️.
- سقف `max_per_user` روی بسته با `0` بگذارید تا هر نماینده بتواند چند پنل بخرد.

## مایگریشن‌ها

مایگریشن‌ها در `src/Support/Migrator.php` تعریف شده‌اند و هر کدام فقط یک‌بار
اجرا می‌شوند:

| نسخه | محتوا |
|---|---|
| `001_core` | جدول‌های پایه: `settings`, `users`, `packages`, `orders`, `payments`, `provision_logs` |
| `002_bot_users` | تنظیمات اولیهٔ فروشگاه و سوییچ‌ها |
| `003_terminal_states` | تفکیک وضعیت `rejected` از خطای موقت + `target_limit` و `panel_applied` |
| `004_payment_guards` | قید یکتایی `(order_id, method)` برای پرداخت‌ها |
| `005_panels` | **جدول `panels`** (چندپنلی شدن) + `test_configs` + مهاجرت دادهٔ کاربران فعلی با `source='legacy'` |
| `006_wallet_backup` | کیف پول کاربران (`wallet_balance`, `wallet_txns`) + زمان‌بندی بکاپ |
| `007_flood_autocard` | جدول‌های ضدتکرار + سوییچ کارت خودکار |
| `008_flood_fingerprint` | اثر انگشت محتوا برای تشخیص آپدیت تکراری |
| `009_agency_extras` | مهلت ارفاقی، آمار کاربران، کد تخفیف، معرفی، فاکتور، تیکت |
| `010_user_limit` | سقف کاربران: `packages.max_users`, `orders.max_users`, `panels.user_limit` |

اجرای مایگریشن با **قفل انحصاری** (`flock` + قفل دیتابیس) محافظت می‌شود تا دو
درخواست همزمان وبهوک هر دو `ALTER TABLE` نزنند. مسیرهای داغ (وبهوک، IPN) فقط
وقتی نسخهٔ کد از آخرین مایگریشن عقب‌تر باشد مایگریشن می‌کنند
(`migrateWhenOutdated`).

## کرون

`cron/worker.php` چند کار انجام می‌دهد:

1. **اجرای خودکار بسته‌های پرداخت‌شده‌ای که هنوز اجرا نشده‌اند**
2. **بررسی خودکار فاکتورهای کارت‌به‌کارت خودکار** (مبلغ یکتا، بدون رسید)
3. **همگام‌سازی خودکار پنل‌ها** از API (با سقف زمانی و گزارش «چند پنل ماند»)
4. **ارسال هشدارها** — حجم کم، انقضای نزدیک، ورود به مهلت ارفاقی، انقضای قطع‌شده
   و پر شدن سقف کاربران (برای خریدار **و** مدیر) + درخواست قطع دسترسی
5. **پاداش معرفی** برای خریداران پرداخت‌شدهٔ معرفی‌شده
6. **پاک‌سازی** کانفیگ‌های تست قدیمی، نشست‌های منقضی و جدول‌های ضدتکرار
7. **بکاپ دوره‌ای** دیتابیس (`off`/`daily`/`twice`) و ارسال آن به سوپرادمین‌ها
8. **گزارش وضعیت** در پایان اجرا

| نکته | توضیح |
|---|---|
| **قفل فایل** | `flock` از اجرای همزمان چند نمونه جلوگیری می‌کند؛ قفل در پوشهٔ `data/` است نه لاگ |
| **ساخت Notifier همیشه fail-safe است** | نبودن `bot_token` نباید کل کارهای دیتابیسی را از کار بیندازد |
| **خطای یک پنل بقیه را متوقف نمی‌کند** | یک نمایندهٔ بی‌پاسخ نباید هزار نمایندهٔ دیگر را متوقف کند |

> اگر دسترسی SSH ندارید، می‌توانید از یک سرویس cron آنلاین (مثلاً cron-job.org)
> که هر ۵ دقیقه `cron/worker.php` را صدا بزند استفاده کنید — ولی نسخهٔ CLI
> مطمئن‌تر است.

همهٔ مجموعه‌ها به‌جز `panel_live_test` **کاملاً آفلاین** هستند و از پنل و تلگرام
قلابی استفاده می‌کنند (هیچ درخواست شبکه‌ای ارسال نمی‌شود). عددشان قطعی است.

`panel_live_test` تنها مجموعهٔ شبکه‌ای است و **تعداد تست‌هایش ثابت نیست**:

- فایل `openapi.json` پنل (حدود ۳۶۰ کیلوبایت) دانلود شود ⇒ **۴۱ تست** که اسپک
  واقعی را با کلاینت مقایسه می‌کند (مسیرها، متدها، پارامترها، فیلدهای ورودی).
- دانلود نشود ⇒ فقط **۷ تست** پایه اجرا می‌شود و بررسی ساختار **ناموفق گزارش
  می‌شود** (بی‌صدا رد نمی‌شود — عمداً، چون «بی‌صدا رد شدن» بدترین حالت برای یک
  نگهبان است).

پس «مجموع کل» بین **۱۱۰۶** و **۱۱۴۰** متغیر است. برای عدد قطعی، مجموعه‌های
غیر از `panel_live_test` را اجرا کنید.

> **نکتهٔ پایداری:** دانلود `openapi.json` از پنل واقعی **گاهی ۴۸ ثانیه** طول
> می‌کشد (اندازه‌گیری شده). به همین دلیل این تست چهار تلاش ۴۰ ثانیه‌ای دارد
> به‌جای یک تلاش کوتاه. اگر این را کم کنید، تست گاهی بی‌دلیل شکست می‌خورد.

> `FakePanelClient` هم اسپک واقعی را mirror می‌کند: `role_id` اجباری (۴۲۲)،
> `listRoles`، `disablePanelUsers` و شمارش وابسته به وضعیت. یعنی تست‌ها دقیقاً
> همان رفتاری را می‌سنجند که پنل واقعی دارد.

## امنیت

| مورد | توضیح |
|---|---|
| **رمز پنل** | با libsodium (یا AES-256-CBC) رمزنگاری می‌شود؛ هرگز خام ذخیره نمی‌شود |
| **وبهوک** | توکن امنیتی در هدر `X-Telegram-Bot-Api-Secret-Token` بررسی می‌شود و **fail-closed** است |
| **وبهوک مدیریتی** | سه دروازهٔ جدا: پیکربندی (۵۰۳) ← توکن (۴۰۳) ← فقط سوپرادمین (نادیده) |
| **فاکتور** | لینک با توکن ۱۲۸ بیتی محافظت می‌شود، نه با شمارهٔ سفارش |
| **IPN — امضا** | HMAC-SHA512 روی **بدنهٔ خام** محاسبه می‌شود (کدگذاری دوبارهٔ JSON امضا را خراب می‌کند) |
| **IPN — مبلغ** | `price_amount` با `amount_usd` فاکتور مقایسه می‌شود (نه `pay_amount` که واحد رمزارز دارد)؛ کم‌پرداختی (`partially_paid`) پرداخت‌شده حساب نمی‌شود |
| **IPN — سفارش** | سفارش با `order_id` **داخلی** پیدا می‌شود، نه با شناسهٔ ناشناس درگاه |
| **IPN — fail-closed** | خطای گذرا سفارش را «ناپرداخت رهاشده» می‌گذارد، نه پرداخت‌شدهٔ جعلی |
| **نقش اپراتور** | نقش مالک هرگز خودکار تخصیص نمی‌یابد |
| **۴۰۳ ≠ باطل‌شدن حساب** | ۴۰۳ روی مسیر عملیاتی یعنی «نقش کافی نیست»، نه خرابی رمز — کاربر بی‌دلیل از فروشگاه بیرون نمی‌افتد |
| **SQL Injection** | همهٔ کوئری‌ها PDO پارامتری هستند؛ نام جدول/ستون با الگوی allow-list اعتبارسنجی می‌شود |
| **XSS در تلگرام** | همهٔ متن‌های کاربر با `Str::escape()` پاک‌سازی می‌شوند |
| **کنترل دسترسی** | پنل مدیریت فقط برای `super_admins`؛ callback با `admin.*` برای بقیه رد می‌شود |
| **دسترسی سفارش** | هر کاربر فقط سفارش‌های خودش را می‌بیند (`findForUser`) |
| **مسدودسازی** | کاربر مسدود به هیچ بخشی دسترسی ندارد |
| **اجرای دوباره** | سفارش `applied` دوباره اجرا نمی‌شود؛ `markPanelApplied` از جمع دوبارهٔ سقف کاربران جلوگیری می‌کند |
| **شارژ مطلق** | شارژ پنل با مقدار مطلق (نه نسبی) اعمال می‌شود؛ شارژ دوباره حجم را دوبار نشمارد |
| **پنل دیگری** | شارژ روی پنلی که متعلق به کاربر نیست **در دو لایه** رد می‌شود: Kernel و Provisioner (چون کرون/IPN هم صدا می‌زنند) |
| **ساخت تکراری پنل** | نام کاربری قطعی است؛ تلاش مجدد همان حساب را بازیابی می‌کند نه حساب دوم |
| **مالکیت پنل** | «من پنل دارم» اجازه نمی‌دهد پنلِ وصل‌شده به حساب دیگری را تصاحب کنی |
| **مشارکت معرفی** | فقط یک معرف برای هر کاربر (قید پایگاه‌داده)؛ خودمعرفی رد می‌شود |
| **تخفیف** | مصرف کد اتمیک است؛ تخفیف هرگز از کل مبلغ بیشتر یا زیر حداقل خرید نمی‌شود |
| **callback_data** | همهٔ داده‌ها زیر ۶۴ بایت (محدودیت تلگرام) نگه داشته شده‌اند |
| **توکن‌ها** | در لاگ‌ها هرگز ذخیره نمی‌شوند |
| **ضدتکرار** | `update_id` + **اثر انگشت محتوا**؛ اکشن‌های سنگین با پنجرهٔ زمانی، ناوبری سبک exempt |
| **قفل worker** | `flock` از اجرای همزمان چند نمونهٔ کرون جلوگیری می‌کند |
| **قفل مایگریشن** | `flock` روی فایل کنار دیتابیس، رقابت بین دو پروسهٔ PHP-FPM را می‌گیرد |
| **سقف زمانی وبهوک** | تماس با پنل بیش از `webhook_budget_seconds` طول نمی‌کشد؛ کاربر پیام تکراری نمی‌گیرد |
| **قطع گروهی** | پایان اعتبار با یک درخواست (`POST …/users/disable`) انجام می‌شود، نه N درخواست |
| **بدنهٔ خالی** | `PUT` با `{}` اصلاً فرستاده نمی‌شود (پنل ممکن است فیلدها را پاک کند) |
| **قرارداد API** | مسیرهایی که پنل ۴۰۵ می‌دهد هرگز صدا زده نمی‌شوند (تست `panel_contract_test`) |
| **فایل‌های حساس** | `.htaccess` مسیرهای `src`/`data`/`tools`/`cron` و فایل‌های `config.php` و `*.sqlite` را می‌بندد |

تست‌های امنیتی این موارد را پوشش می‌دهند (`php tests/security_test.php` و

XSS، عدم تکرار اجرای بسته، جعل امضای IPN و عدم پذیرش کم‌پرداختی.

## جلوگیری از هنگ کردن ربات

تلگرام بعد از ۶۰ ثانیه بی‌پاسخ ماندن، پیام را **دوباره** می‌فرستد. اگر پردازش
ما بیشتر طول بکشد، سه اتفاق بد می‌افتد: پیام تکراری برای کاربر، بارگذاری دوبارهٔ
پنل، و قفل شدن دکمه‌ها توسط `FloodGuard`.

بدترین حالت یک فراخوانی ساده به پنل، بدون سقف:

```
login  = ۲ تلاش × ۲۰ ثانیه = ۴۰ ثانیه
send   = ۲ تلاش × ۲۰ ثانیه = ۴۰ ثانیه
۴۰۱ → یک دور کامل دیگر      = ۸۰ ثانیه
جمع                        = ۱۶۰ ثانیه
```

| نگهبان | کارش |
|---|---|
| `webhook_budget_seconds` | سقف کل یک پیام؛ `timeout` هر درخواست با وقت باقی‌مانده کوتاه می‌شود |
| نگهبان پیش از درخواست | وقتی کمتر از ۲ ثانیه مانده، **شبکه لمس نمی‌شود** و خطای روشن می‌آید |
| حذف تلاش مجدد بی‌فایده | وقتی برای یک دور کامل وقت نیست، `attempts = 1` |
| سهمیهٔ کل پروسه | همهٔ کلاینت‌هایی که در یک درخواست ساخته می‌شوند سقف می‌گیرند |
| `cron_budget_seconds` | کرون پنل‌های باقی‌مانده را به اجرای بعدی می‌سپارد و تعدادشان را می‌گوید |
| **آمار کاربران** | ۳ شمارش ارزان (`limit=1` + تکرار کلیدهای وضعیت) به‌جای ده‌ها صفحه؛ اگر اعداد با هم نخوانند، به walk کامل برمی‌گردد |
| **قطع دسترسی** | مسیر گروهی پنل؛ در مسیر تکی هم صفحه‌بندی **کامل** (نه فقط ۱۰۰ تای اول) با سقف `MAX_PER_RUN = 200` و بودجهٔ زمانی |
| **گزارش صادقانه** | اگر تعداد کاربران باقی‌مانده معلوم نباشد، صریحاً «تخمینی» گفته می‌شود، نه عدد ساختگی |
| **فیلتر ادمین** | در قطع دسترسی و شمارش سریع، `admin={نام کاربری}` ارسال می‌شود تا کاربران کل پنل شمرده نشوند |

کرون و CLI سقف تلگرام ندارند، پس پیش‌فرضِ **بدون سقف** می‌مانند.

> اگر پنل شما از `POST /api/admin/{u}/users/disable` استفاده نکند، ربات
> خودکار به مسیر تکی برمی‌گردد و سقف اجرا را هم رعایت می‌کند.

### ضدتکرار (`FloodGuard`)

دو لایه، هر دو **fail-open** (اگر دیتابیس در دسترس نباشد، دستور اجرا می‌شود تا
ربات مختل نشود):

1. **آپدیت تکراری** — فقط «همان `update_id` + همان اثر انگشت محتوا» تکراری است.
   اگر همان عدد با محتوای متفاوت دیده شود، آپدیت واقعی است.
2. **پنجرهٔ اکشن‌های سنگین** — `pkg.buy` (۸ ثانیه)، `pay` (۸)، `panel.sync`،
   `panel.refresh`، `user.refresh` و `panel.test` (۱۰)، `order.check` (۵) و
   اکشن‌های ادمین حساس مثل `admin.retry` (۱۰) و بکاپ/پخش/قطع (۳۰). ناوبری سبک
   (منو، دیدن پنل، صفحهٔ بعد) **محدود نمی‌شود** تا تجربهٔ کاربری خراب نشود.

رسید تصویری تکراری در پنجرهٔ ۵ ثانیه و پیام متنی یکسان در پنجرهٔ ۲ ثانیه رد
می‌شوند. کرون ردیف‌های قدیمی هر دو جدول را پاک می‌کند.

### توصیه‌ها

- `crypto_key` را بعد از ثبت اطلاعات کاربران **عوض نکنید** (اطلاعات قبلی رمزگشایی نمی‌شوند).
- `config.php` و پوشهٔ `data/` را از دسترس عمومی خارج نگه دارید (فایل `.htaccess` این کار را می‌کند).
- برای دیتابیس، دسترسی `data/` را در سطح سرور هم ببندید.
- **بکاپ‌ها را جایی نگه ندارید که لو برود** — داخلشان رمز رمزنگاری‌شدهٔ
  پنل‌های نمایندگان است و با `crypto_key` قابل رمزگشایی‌اند.
- قبل از هر تغییر ساختاری `php tools/cli.php backup` را بزنید.
- `admin_webhook_secret` باید **متفاوت** از `webhook_secret` باشد؛ وگرنه هر
  کسی که به ربات اصلی دسترسی دارد می‌تواند به ربات مدیریتی هم پیام بدهد.
- `expire_grace_days` را صفر نگذارید مگر اینکه عمداً می‌خواهید قطع دسترسی
  بلافاصله بعد از انقضا اتفاق بیفتد.
- اگر روی پنل فقط یک نقش (مالک) وجود دارد، خرید پنل نمایندگی عمداً متوقف
  می‌شود. یک نقش اپراتور بسازید.

## نکته دربارهٔ اجرای خودکار

سیستم برای اجرای بسته **idempotent** طراحی شده است:

- سفارش با وضعیت `applied` **دوباره اجرا نمی‌شود** (حتی اگر دکمهٔ اجرا دوباره زده شود).
- هدف مطلق سقف (`target_limit`) یک‌بار محاسبه و ذخیره می‌شود؛ تلاش مجدد همان عدد
  را دوباره می‌نویسد، نه `سقف فعلی + حجم`.
- `panel_applied` مشخص می‌کند چه زمانی روی پنل اعمال شده تا سقف کاربران هم فقط
  یک‌بار جمع شود.
- هر اجرا در جدول `provision_logs` ثبت می‌شود.
- **۴۰۱** (یا ۴۰۳ روی مسیر صدور توکن) باعث `revoked` شدن پنل می‌شود تا نماینده
  دوباره ثبتش کند.
- **۴۰۳ روی مسیر عملیاتی** فقط `permission_denied` ثبت می‌شود؛ حساب سالم می‌ماند.
- خطاهای موقت (5xx، 429، خطای شبکه) با تأخیر نمایی تکرار می‌شوند.
